Bibliografía PAGEREF _Toc229492264 \h 16 INTRODUCCIÓN El presente documento corresponde al Plan de Aseguramiento de Calidad (SQA) para el desarrollo del Sistema de Tickets orientado al Servicio de Recursos Físicos del Hospital HRR. Este sistema busca digitalizar y sistematizar la gestión de solicitudes de mantención, reparación y apoyo operativo del servicio. El plan define los objetivos, alcances, responsables, procesos, estándares y herramientas que se utilizarán para garantizar que el software desarrollado cumpla con los requisitos funcionales y no funcionales establecidos, asegurando su calidad, trazabilidad y confiabilidad antes de su puesta en producción. OBJETIVOS Y ALCANCES Descripción del Proyecto El proyecto consiste en el desarrollo e implementación de un sistema de tickets orientado al Servicio de Recursos Físicos de un hospital, que permitirá registrar, gestionar y dar seguimiento a las solicitudes de mantención, reparación y apoyo operativo. El sistema considerará la creación de tickets por parte de unidades solicitantes, su asignación al personal técnico correspondiente, el registro de avances y el cierre conforme con recepción de conformidad. Además, generará reportes e indicadores clave de desempeño (KPIs) para la jefatura del servicio. Objetivos del Plan Asegurar que el sistema de tickets cumpla con todos los requerimientos funcionales definidos por el equipo y validados con el cliente. Garantizar el correcto funcionamiento, facilidad de uso y confiabilidad del sistema antes de su entrega. Detectar y gestionar errores mediante pruebas y controles sistemáticos durante el ciclo de desarrollo. Establecer roles, responsabilidades y procesos formales de calidad para el equipo de desarrollo. Definir métricas que permitan medir y monitorear la calidad del producto durante y después del desarrollo. Alcance del Plan El plan de calidad considera todo el proceso, desde revisar que los requerimientos estén bien definidos hasta comprobar que el sistema funcione correctamente una vez implementado. Lo que se enfoca en las funciones principales, como crear tickets, asignarlos, hacer seguimiento y cerrarlos, asegurando mediante pruebas y validaciones con usuarios que todo opere de forma correcta. Restricciones El plan de calidad tiene algunas limitaciones, como el uso de herramientas básicas para realizar las pruebas, el tiempo disponible para validar completamente el sistema y la falta de integración con otros sistemas del hospital. Además, no contempla el mantenimiento posterior ni la gestión de recursos externos. Las pruebas se realizarán con herramientas de acceso libre o gratuito disponibles para el equipo. El tiempo disponible para validación completa está sujeto al calendario académico del semestre. No se gestionan recursos externos ni contratos con terceros proveedores. Se prohíbe ejecutar consultas SQL con datos sin validar para prevenir inyecciones SQL y ataques XSS. Alejandro / Leandro Gestión de secretos Las contraseñas, tokens de API y llaves de base de datos no deben subirse al repositorio. Se utilizarán variables de entorno (.env) excluidas del control de versiones (.gitignore). Alejandro Principio de menor privilegio Cada usuario del sistema accederá únicamente a las funciones necesarias para su rol. Un técnico no puede eliminar registros de auditoría; solo la jefatura puede generar reportes completos. Eduardo Control de versiones Todo el código fuente se gestionará mediante Git con ramas separadas por módulo. Ningún cambio se integrará a la rama principal sin pasar por revisión entre pares. Eduardo Cifrado de comunicaciones El sistema deberá operar bajo HTTPS. Las contraseñas de usuarios se almacenarán con hash usando algoritmos seguros (bcrypt o Argon2), nunca en texto plano. Alejandro Crear Políticas de Gestión de Responsabilidades Política / Práctica Descripción Responsable Propiedad del código (Code Ownership) Se definen responsables por módulo: Alejandro para Backend, Diego para Frontend, Leandro para Base de Datos. Todo cambio debe ser revisado por un integrante distinto al autor antes de ser integrado. Alejandro Gestión de incidencias Los errores críticos deben ser tomados por el responsable del módulo afectado en un plazo máximo de 24 horas. Se documentará el error, la causa raíz y la solución aplicada en el repositorio. Eduardo Documentación obligatoria Cada nueva funcionalidad debe acompañarse de documentación técnica (descripción, endpoints, estructura de datos) y de usuario (manual de uso). Sin documentación, la tarea no se considera finalizada. Todo el equipo Revisión entre pares Antes de declarar una tarea como terminada, un integrante distinto al autor debe revisar el código o artefacto. La revisión se registra con firma en el checklist de calidad. Eduardo (coordina) Crear Políticas de Respaldo Política / Práctica Descripción Responsable Frecuencia de respaldo Se realizarán respaldos automáticos diarios de la base de datos del sistema. Los respaldos se comprimirán y nombrarán con fecha y hora para facilitar su identificación. Leandro Regla 3-2-1 Se mantendrán al menos 3 copias de los datos en 2 soportes distintos (disco local del servidor y almacenamiento en la nube), con 1 copia fuera del sitio principal del hospital. Leandro / Alejandro Pruebas de restauración Una vez al mes se realizará una prueba de restauración de respaldo en el entorno de desarrollo para verificar la integridad y funcionalidad del backup. El resultado se documentará. Leandro Retención de respaldos Los respaldos diarios se conservarán por 30 días. Los respaldos semanales se conservarán por 3 meses. Los respaldos mensuales se conservarán por 1 año. Eduardo Pirámide de pruebas Se seguirá la pirámide de pruebas: pruebas unitarias en la base (mayor cantidad), pruebas de integración en el centro, y pruebas de aceptación UAT en la cima. Eduardo Trazabilidad de defectos Todos los defectos detectados se registrarán en una tabla de seguimiento con identificador único, descripción, severidad, estado y responsable de corrección. Eduardo Ambientes de prueba Las pruebas se ejecutarán en un ambiente de desarrollo/staging separado del entorno de producción. Ninguna prueba se realizará directamente en producción. Alejandro / Eduardo IDENTIFICAR Y SELECCIONAR LOS ESTÁNDARES Y PAUTAS Identificar Normas de Referencia ISO/IEC 25010 (Calidad del producto de Software): Se selecciona este estándar porque proporciona un marco detallado para evaluar la calidad del sistema de tickets cuando se construya. El propósito en el proyecto será asegurar que el software cumpla con las características esperadas por los usuarios del hospital, evaluando aspectos críticos y la seguridad funcional de la plataforma. ISO/IEC 12207 (Procesos del Ciclo de Vida del Software): Se utilizará esta norma para estandarizar el proceso de desarrollo y gestión del ciclo de vida del sistema. Porque el software requiere de varias etapas diferentes, este estándar hará que tenga un orden metodológico, asegurando la calidad y efectividad en cada fase de la construcción. MODELO CMMI ( Capability Maturity Model Integration ) e ISO/IEC 33000: Se tomarán los principios de evaluación de procesos organizativos propuestos por estos modelos. El objetivo será garantizar que las prácticas del equipo de desarrollo (la forma en que se gestionan los requerimientos, las pruebas y los entregables) sean eficientes, buscando una mejora sistemática continua para asegurarnos de que el sistema que entreguemos al hospital no va a fallar.
